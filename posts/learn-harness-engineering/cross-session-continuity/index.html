Learn Harness Engineering

让跨会话的任务保持上下文连续

通过进度文件、决策日志与 Git 提交，让跨会话的长任务保持上下文连续。

一句话总结 上下文窗口再大也会用完。解决跨会话连续性的关键不是更大的窗口，而是把 Agent 当成每天清空记忆的工程师 —— 用 进度文件 + 决策日志 + git 检查点 三件套写好交接。
你让 Claude Code 实现一个完整功能，它跑了 30 分钟，做了大部分工作，但上下文快满了。开个新会话继续 —— 它不记得上次的决策、为什么选方案 A、哪些文件改过、测试跑到哪了。它得花 15 分钟重新探索一遍，而且可能跟上次不一致。

​
🔍 问题本质

​
上下文窗口的有限性，不是模型问题

即使窗口扩到 1M tokens，复杂任务依然会用完。因为 agent 不只是生成代码，它还要理解代码库、跟踪决策历史、处理工具输出、维护对话上下文 —— 这些增长得比窗口扩容快得多。

​
更深的问题：信息不是均匀重要的

信息类型包含内容压缩后
中间推理（为什么）方案 A vs B 的取舍、库选型、跳过某优化的理由通常丢失
最终输出（是什么）代码本身保留
下一个会话看到代码却不知道为什么这么写，可能会“优化”掉一个有意为之的设计决策。

​
🧠 四个关键概念

  • 重建成本：新会话恢复到可执行状态所需的时间。好的 harness 能把这个时间从 15 分钟 压到 3 分钟 以内。
  • 漂移 (Drift)：agent 的理解与代码仓库实际状态之间的偏差。每次会话边界都会引入漂移，不加控制会越漂越远。
  • 上下文焦虑：Anthropic 观察到的现象 —— agent 接近上下文限制时表现异常，过早结束任务、跳过验证、选简单方案而非最优方案，本质上是一种非理性的资源焦虑。
  • 压缩 vs 重置：两种应对策略，特性截然不同（见下）。

​
⚖️ 压缩 vs 重置

压缩 (Compaction)重置 (Context Reset)
做法同会话内摘要化早期对话开新会话，从持久化工件重建
保留“是什么”（连续性）干净的心理状态，无焦虑
丢失“为什么”（决策上下文）未写入工件的信息
依赖摘要质量交接工件的完备性
Anthropic 实测：Sonnet 4.5 上下文焦虑严重，压缩不够用，重置成为关键；Opus 4.5 行为大幅减弱，可主要靠压缩管理。 → Harness 设计需要针对具体模型，而不是套用通用模板。

​
🛠️ 实践方法：三件套

核心思路：把 agent 当成每次会话都会清空短期记忆的工程师。下班前必须写下交接信息，让接班的 agent 能快速上手。

​
1. 进度文件 · PROGRESS.md

回答“现在在哪、卡在哪、下一步去哪”。

模板示例

# 项目进度

## 当前状态
- 最新 commit: abc1234 (feat: add user preferences endpoint)
- 测试状态: 42/43 通过 (test_pagination_edge_case 失败)
- Lint: 通过

## 已完成
- [x] 用户模型和数据库迁移
- [x] 基础 CRUD 端点
- [x] 认证中间件集成

## 进行中
- [ ] 分页功能 (90% - 边界条件测试失败)

## 已知问题
- test_pagination_edge_case 在空结果集时返回 500
- 需要确认是否要在列表中包含已删除用户

## 下一步
1. 修复分页边界条件 bug
2. 添加"是否包含已删除用户"的查询参数
3. 更新 API 文档

​
2. 决策日志 · DECISIONS.md

回答“为什么这么做” —— 保住会被压缩丢掉的关键信息。只记“什么决策、为什么、什么时候”，不写详细设计文档。

模板示例

# 设计决策

## 2024-01-15: 使用 Redis 缓存用户偏好
- 原因: 读取频率高（每次 API 调用都需要），数据量小
- 否决方案: PostgreSQL 物化视图（变更频率高，维护成本不划算）
- 约束: 缓存 TTL 设为 5 分钟，写入时主动失效

​
3. Git 提交 · 自动检查点

每完成一个原子工作单元就提交，commit message 说清做了什么和为什么。免费的、自动版本化的状态快照。

​
🔄 上下班流程（写进 AGENTS.md）

会话开始（上班）
  1. 读 PROGRESS.md 了解当前状态
  2. 读 DECISIONS.md 了解重要决策
  3. 跑 make check 确认仓库一致
  4. 从“下一步”继续工作
会话结束（下班）
  1. 更新 PROGRESS.md
  2. 跑 make check 确认一致状态
  3. 提交所有已完成的工作

​
🎚️ 混合策略：何时该交接？

判断标准：任务所需上下文超过窗口的 60%，就开始准备交接。
  • 短任务（< 30 分钟）：会话内完成，不必折腾持久化。
  • 长任务（跨会话）：必须用进度文件 + 决策日志维持连续性。

​
📊 实际效果（Anthropic 案例）

带认证的博客系统，12 个功能点，预计 5 个会话：
指标无持久化有持久化
会话 2 重建时间~15 分钟~3 分钟 (↓78%)
功能完成率58% (7/12)100% (12/12)
隐含缺陷率43%8%

​
✅ 核心要点

  • 上下文窗口是有限资源，跨会话一定会丢信息 —— 这是客观现实
  • 解决方案不是更大窗口，而是更好的状态持久化。
  • 重建成本是衡量 harness 质量的关键指标（目标：≤ 3 分钟）。
  • 短任务会话内做完；长任务用结构化工件维持连续性。
  • Harness 设计要针对具体模型 —— Sonnet 4.5 重视重置，Opus 4.5 可靠压缩。
